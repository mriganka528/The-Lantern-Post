## Deliverable

A user signs up through a managed provider, chooses a unique username, and lands on an empty home screen. The session survives app restarts. Phase 2 character/palace features are outside this phase.

## Accepted decisions

1. **Provider:** Clerk, selected by the user.
2. **Sign-in methods:** email verification codes and Google, approved by the user. Google is already enabled in the Clerk dashboard.
3. **Account rules:** 13+ self-confirmation and case-insensitive usernames of 3–24 lowercase letters, digits, or underscores, approved by the user. No date of birth is collected.
4. **Database:** the user supplied a Neon PostgreSQL URL and requested it for database activity before the next phase. The root `.env` is the database configuration source; Docker is optional.

Use the existing Clerk development application. The client takes the publishable key; the server takes that same public key and the secret key. Keep the secret out of Expo. No manual issuer or JWT public key is required. The agent has not created a provider account or sent verification email.

## Prepared code

- Clerk's Expo provider and SecureStore token cache; protected navigation waits for session hydration.
- Email and Google sign-in/sign-up, age confirmation before account creation/provider handoff, callback handling, code verification, resend cooldown, and safe error messages.
- Username selection with debounced availability checking and the empty authenticated home screen.
- A fresh TanStack Query cache for each Clerk session. Token retrieval is bound to the originating session so old requests cannot retry under another account. Zustand holds temporary onboarding UI state only.
- NestJS bearer verification through Clerk's backend SDK with automatic signing-key retrieval, plus trusted-issuer, session, expiry, and authorized-party checks. Production requires public/secret keys; incomplete development configuration fails closed for authenticated routes.

- Shared contracts for the authenticated owner's profile, an optional existing profile, and username availability.
- A Prisma-backed `UsersService` that looks up a profile by its verified managed identity, creates the initial user, and handles uniqueness conflicts.
- Explicit profile selection and serialization that omit `authProviderId` and unexpected private fields.
- Safe repeat onboarding: replaying the same username returns the existing profile, while changing a username through this path is rejected. Username-change/cooldown functionality is not part of the Phase 1 initial-username flow.
- Tests covering first-time creation, private-field omission, repeats, competing username claims, concurrent creation for the same account, and database failures.

The root API now exposes guarded `GET /users/me`, `GET /users/username-availability`, and `POST /users/me` routes. Identity comes exclusively from the verified token. Age and username validation run server-side. A separate SQL migration enforces lowercase username format for all database writers; the Prisma schema itself remains identical to `04_DATA_MODEL.md`. Existing invalid names cause migration failure rather than an automatic rename.

## Neon connection changes

The API and Prisma CLI load the root `.env` before API-specific settings. The obsolete local `DATABASE_URL` was removed from `apps/api/.env`. Runtime queries use the pooled connection; migration commands derive the matching unpooled endpoint or accept a validated `DIRECT_URL`. Neon connections require TLS and receive default connection timeout/pool settings only when not explicitly supplied. Development migration commands require a separate shadow database/branch, and validation prevents the application database being used as its own shadow. No model, relation, or checked-in migration SQL changed for Neon.
